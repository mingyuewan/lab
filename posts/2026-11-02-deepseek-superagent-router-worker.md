人的注意力，而不是模型能力，已经成为 Agent 多任务的瓶颈。

2026 年 10 月 31 日，DeepSeek Harness 团队在 X 上发布长文《Exploring Super-agent Design: Towards a More Autonomous Agent System》（中文原标《Super-agent 设计探索：迈向更自主的 Agent 系统》），并同步开源研究原型 [dsh-superagent-prototype](https://github.com/deepseek-ai/dsh-superagent-prototype)。主帖获得 8700+ 赞、近 110 万次浏览。文章不是新模型发布，而是一套系统架构方案：让 Agent 从单一 Session 的聊天窗口解脱出来，变成跨信道连续、并行多任务、事件驱动主动、持久在线的实体。<grok type="render_inline_citation" citation_id="32" />

## 事件还原

团队指出，过去一年 coding agent 已能少人干预解决复杂任务，但主流设计仍以单一 Session 为基本单位。用户并行多任务时必须手动切换 Session、记住各自上下文。他们的经验是，一个人通常只能跟住 3–5 个活跃 Session。单任务上限看模型，多任务上限看人的注意力。

解法是把 Agent 从单次手动会话解耦，做成一个能跨会话保持上下文、同时推进多项任务且互不干扰的连续实体。他们把这种形态称为 Super-agent，并归纳四项基础特征：

- **连续**：用户在 IM、GitHub 评论等不同信道与同一个 Agent 交互，不用担心「Session X 里有没有 Y」。
- **高效**：并行完成多个复杂任务，不必等上一条做完才能下一条。
- **主动**：持续观察环境事件（群聊、CI、评论），值得处理才出手，否则保持安静。
- **持久**：始终在线，直接接入真实工作环境，异常自动恢复。

单个 ReAct Loop 无法同时满足这四点，必须靠系统架构。他们提出五个模块：双层架构、事件驱动、全双工多信道交互、存算分离、外部 Watchdog。

同日开源的原型是 DeepSeek Harness 的一个 bundle，面向单个 GitHub 仓库（可选飞书），监听通知，只有授权人士请求或团队写好的规则允许时才行动，在独立会话与目录里工作，最后回到原对话交付（例如提 PR）。README 明确说明：这是研究原型，不是官方产品；代码与文章描述的内部实现不完全一致，部分设计仍是未来方向。<grok type="render_inline_citation" citation_id="58" />

## 作者与产品背景

DeepSeek Harness（dsh）是 DeepSeek 开源的 Agent Harness，基于 Cordis 「一切皆插件」架构：模型适配器、工具注册表、会话日志、Agent Loop 本身都是可替换插件。官网与 GitHub 显示它处于开发者预览阶段，支持 Web UI、桌面端，以及通过 npx 或源码启动。官方仓库已超 26 万星。Super-agent 是在这个 Harness 上的一层产品与架构探索，而不是另一个模型。

文章中举例：内部运行的 Super-agent 实例可以在 IM 与 GitHub 之间连续推进同一个开发任务；在公开群聊无人 @ 的情况下也能识别缺陷、后台复现并提交修复 PR。原型的哲学文档明确原则：「尽可能少占用人的注意力，尽可能多提供价值」——只有被问或规则允许才行动，只在需要人决策或可用结果时才说话。

## 方法论与架构拆解

**双层架构**是核心。Router 层是常驻全局路由会话：接收所有人类交互、维护全局上下文与协调，只分派任务，不亲自执行（甚至可以不配 Bash），因队经验中较轻模型就够。Worker 层是上下文隔离的执行会话，挂满工具，专注单一任务，用最强模型；Worker 不直接对用户说话，结果汇报给 Router，由 Router 统一回复。这解决了连续性与吞吐量的权衡：全进一个 Session 会串行且污染上下文，每事新开 Session 则缺乏全局视图。

**事件驱动**。主输入从人逐条打字变成环境 Trigger（群聊消息、代码评论、CI 结果等）。两级过滤：程序层 Fast Path 按来源、白名单等确定性规则剔噪音；语义层 Slow Path 才交给 LLM 判断是否行动。订阅与直通：Worker 认领某条 Thread（如一个 PR）后，后续事件直接交给该 Worker，Router 只处理冷启动与跨任务协调。上下文组织借用 Inline & Spill：把上下文窗口当缓存，常用信息内联，长内容溢出到外部并留指针；Chain of Recall 让模型按需跳式召回更多。还有投机执行：根据环境信号后台预先工作，有用才交付。

**交互与持久**。异步 ReAct（start/stop 代替阻塞式 run）实现全双工，背景任务不堵住前台对话。多信道按场景调整详细程度（IM 短回复、GitHub 结构化输出）。存算分离：Agent Loop 在云端无状态容器，会话状态持久化；执行环境（仓库、本地工具链）留在原地，通过轻量 daemon 连接（BYOM）。外部 Watchdog 会话监控进展与异常，不仅看进程是否还活，也判断是否偏离目标。

原型实现上有 Engine、Ticket、Assignment、Trigger/Thread 等概念，与文章中的逻辑层对应，但代码明确是适配后的研究代码。

## 实验数字

团队自己做了初步实验（合成负载、简化环境，结果仅供参考）。约 300 条消息（约 20 条工作请求）驱动，编码工作用只耗时工具模拟，每种方案跑 5 次。衡量的是调度协调，不是真实代码质量。

- Super-agent：p50 12.4 分钟，p95 15.7 分钟
- 单 Session + Subagent（中性提示）：p95 29.5 分钟（模型基本不委派，全在主 Session 做并被中断）
- 单 Session + 优先委派提示：仍慢于 Super-agent，有长尾

去掉直通后完成时间基本一致，但 Router 决策数增加约 30%，读缓存 token 从约 23.2M 升到 31.8M（约 +37%）。Router 批处理实验显示，事件到达率从约 1 到 40 次/分钟时，分摊推理时间从 6.4 秒降到 1.6 秒。数字来自团队文章及多家二手报道一致转述，尚未见独立第三方复现。<grok type="render_inline_citation" citation_id="91" />

## 争议与反方

最大的限制是自己说的：原型不是产品，实验是合成的，没有衡量真实代码质量。多人指出，双层架构本身不新，更像把计算机系统里的调度、缓存、存算分离、Watchdog 搬到 Agent 上。开放问题包括：如何在更大规模下分片 Router 而不损失全局上下文、无 Session 产品形态怎么设计、跨实例 A2A 如何安全协作、事件驱动带来的不可信输入风险。

与其他方案对照：单会话 + Subagent 依赖提示词与模型临场判断，容易不委派；传统 Agent Team 更重视紧耦合任务拆解与频繁协调。Super-agent 的 Router 故意不拆任务、只做高层分派。

## 可迁移的做法

1. **把 Session 从用户心智中拿掉**：用户只面对一个 Agent，系统负责上下文与并发。
2. **分派与执行分层**：轻量 Router 只说话和分派，强模型 Worker 专注干活，减少主会话被长任务阻塞与上下文污染。
3. **事件优先于提示**：用两级过滤 + 订阅直通，让系统能主动但不刷屏。
4. **注意力预算**：每条消息、每个问题都要问「值不值得打断人」，主动工作先记录再放开。
5. **外部监控**：不仅看进程活性，还要判断任务是否还在有效推进。

这些不依赖特定模型，也不依赖 DeepSeek Harness。

## 未核验项

- 实验数字仅来自团队自述与二手报道，无独立复现；且未衡量真实代码质量。
- 原型与文章描述的内部实现差异程度，需要读代码确认。
- 内部运行实例的真实效果与长期稳定性无公开数据。
- 安全与隐私章节被截断，完整设计未公开。
- 对照帖（如 Karpathy HackerTube、其他 multi-agent 实践）仅作背景，未做深度比较。
