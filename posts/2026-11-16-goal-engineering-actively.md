**一句话判断：** 当 Agent 从执行任务转向追求开放目标时，真正决定可靠性的不是更强的模型，而是把目标范围设计成“人类容易给出高质量反馈”的形状。

## 事件还原

2026 年 11 月 14 日，LangChain 联合创始人 Harrison Chase 与 Actively AI 的 Mihir Garimella、Anshul Gupta 联名发表了一篇《Goal Engineering: How to Design Goals》。帖子较短，但核心观点很尖锐：

> 你要设计 Agent 的范围，使得在这个范围内人类越容易给出反馈。

他们指出，Agent 失败很多时候不是因为缺了 API 或文档，而是缺了“从来没有被写下来的上下文”——也就是人脑子里的品味、策略偏好、品牌边界。这类信息只能通过人类专家的反馈注入。因此，目标设计应该优先服务于“反馈效率”，而不是抽象上的业务对象（比如“每个账户一个 Agent”）。

帖子以 Hone 的 Engines（持久性、拥有业务结果的 AI）作为远景参照，并以 Actively AI 的产品演化为案例。

## 作者与产品背景

Harrison Chase 是 LangChain 的创始人，近年把精力放在 Agent harness（Deep Agents）、上下文工程和现在提出的 goal engineering。

Actively AI 由 Stanford AI 研究者 Mihir Garimella（CEO）和 Anshul Gupta 共同创办，专注销售/收入团队的 AI Agent。公司已完成多轮融资（含 2026 年 4 月的 $45M Series B，累计约 $68M），客户包括 Ramp、Samsara、Ironclad、Zillow Rentals 等。公开定位一直是“Per-Account Agents”——每个账户一个持久 Agent，7x24 监测并推进动作。

Deep Agents 是 LangChain 开源的意见性 harness，内置规划、文件系统上下文、子 Agent 委派等，Actively 的新版本正是基于它构建。

## 方法论与架构拆解

Actively 的演化很说明问题：

**第一版：每账户一个 Agent。**  直觉合理——账户是销售的核心对象，上下文也多在账户里。但实际上，销售代表要学习的是“怎么做出站”“怎么回复”“多激进”“如何穿越大组织”这些跨账户的技能与品味。这些学习散落在不同 Agent 上，且每个账户 Agent 在任一时间点只有少量任务需要审核，导致销售代表频繁切换上下文，反馈成本高、跨 Agent 知识迁移糟糕。

**第二版：Motions（按工作类型划分）。**  
一个 motion 代表一类可复盘的工作，例如“outbounding”或“early-stage deal progression”。同一 motion 下的任务高度相似，销售代表可以集中审核一批，反馈自然跨账户传播。账户上下文仍由后台专门的 context-gathering Agent 维护，motion Agent 按需拉取。

这种切分把“容易反馈的主观技能”与“已经写下来的客观上下文”解耦，让学习速度大幅提升。

帖子还强调：投资于清晰、低摩擦的审核 UX。因为瓶颈往往不是模型能力，而是人类愿不愿意、能不能高效地提供反馈。

## 争议与反方

- **目标容易被钻空子**：多位回应者指出，优化“回复率”会学会点击诱饵；目标必须是你真正愿意为之付费的结果，再加上不能交易的约束。
- **目标必须可验证**：有人认为，没有明确停止条件或验收检查的目标只是愿望。
- **范围传播问题**：反馈应该应用到多广？“写短一点”是只对这一封邮件，还是所有未来邮件？需要明确的范围控制。
- **与公开叙事的张力**：Actively 官网仍强调 Per-Account Agents，而帖子描述的是向 motions 的演进。这可能是产品迭代中的内部学习，也可能是两层架构（账户上下文 + 工作类型 Agent）并存。

## 可迁移的做法

1. **先问“这个范围里人类怎么快速审核？”** 而不是“这个对象从业务上是否自然”。
2. **把容易迁移的学习**（策略、品味、话术）与**难以迁移的上下文**（具体账户历史）分开存储。
3. **为反馈设计专门 UX**：批量审核、一键批注、明确的范围选择。
4. **给目标加约束与停止条件**，避免钻空子。
5. **在引入完全自主前**，先把反馈循环跑通。

## 未核验项

- Actively 当前生产环境究竟是“纯 motions”还是“账户 Agent + motion 层”的混合架构，官方并无公开技术详情。
- Hone Engines 的实际客户效果与持久运行数据尚未独立验证。
- “反馈优先”在其他领域（编程、研究、客服）的通用性需要更多案例。
- Deep Agents 作为底层的具体贡献（规划、子 Agent、文件系统）在此场景中的权重未定量。
